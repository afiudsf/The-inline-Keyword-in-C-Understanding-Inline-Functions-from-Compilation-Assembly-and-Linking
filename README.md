# The-inline-Keyword-in-C-Understanding-Inline-Functions-from-Compilation-Assembly-and-Linking

开始学习 C 语言时，我曾把 `inline` 关键字理解得十分直接：在函数前面加上 `inline` 关键字后，编译器就会把函数代码复制到调用位置，省掉函数调用，程序自然会更快。然而在真正学习编译和链接之后，才会发现事情没有想的这么简单：有时加了 `inline`，程序仍然生成了函数调用；有时代码可以编译，却在链接阶段报出 `undefined reference`；把编译选项从 `-O0` 改成 `-O2`，结果又变了。

因此本文将从一个简单函数开始，说明 C 语言中的 `inline` 到底有什么作用，为什么 `inline` 通常与 `static` 一起使用，以及怎样从汇编代码的角度去理解。因为本文涉及大量汇编代码的知识，因此建议在阅读本文之前先预先对汇编的知识有一定的了解。

## 一、什么是内联函数

先看一个普通函数：

```c
int add(int a, int b)
{
    return a + b;
}

int main(void)
{
    int result = add(1, 2);
    return result;
}
```

程序执行到 `add(1, 2)` 时，需要跳转到 `add` 函数。函数执行完，再返回到 `main`。这个过程除了加法本身，还包括参数传递、保存返回地址、跳转和返回等入栈出栈操作。如果函数很小，却被调用了很多次，这些额外步骤就可能占去相当一部分时间。

因此为了提供整体效率，我们可以建议编译器把函数内部的代码直接放到调用位置取代每一处调用该函数的地方，而这种优化叫作内联。

```c
inline int add(int a, int b)
{
    return a + b;
}
```

假设编译器决定把它内联，那么 `int result = add(1, 2)` 会在编译阶段（开启 LTO 后，部分内联可能会推迟到链接阶段）时由编译器在优化过程中完成接近于 `int result = 1 + 2` 的存在。要注意的是，这里的“可能”是不能省略，因为 `inline` 只是给编译器的建议，而不是强制命令。比如说在使用 `-O0` 时，编译器通常会尽量保留源代码结构；而在使用 `-O2` 或 `-Os` 时，编译器会进行更多优化。

不过，优化级别高也不代表所有 `inline` 函数都会展开。内联主要是减少调用过程，提供运行效率的，不是专门用来解决栈空间不足的。实际的栈使用情况还取决于函数内容、调用约定、编译器和处理器。

## 二、从汇编码深入理解inline

下面我们从汇编的角度深入理解一下 `inline` 关键字的使用。

首先我们先看一个普通的多文件程序：

```c
/* add.h */
int add(int a, int b);

/* add.c */
int add(int a, int b)
{
    return a + b;
}

/* main.c */
#include "add.h"
int main(void)
{
    return add(1, 2);
}
```

```bash
gcc -c add.c
gcc -c main.c
gcc add.o main.o -o main
```

在编译 `main.c` 时，编译器只看到了函数声明，看不到函数体。因此，编译器暂时不能把 `add` 的具体指令直接放进 `main`，只能先生成一个函数调用。`main.o` 中会保留对 `add` 的引用，等到链接阶段，链接器再从 `add.o` 中找到真正的 `add` 函数。

在 Cortex-M3/M4 中，普通函数调用通常会使用 `BL` 指令进行调用：

```asm
    MOVS    r0, #1
    MOVS    r1, #2
    BL      add
add:
    ADDS    r0, r0, r1
    BX      lr
```

从这几条指令可以看出，一次普通函数调用至少包含两部分工作。第一部分是函数真正要完成的加法，第二部分是为了完成调用和返回而执行的跳转、返回地址保存以及相关的寄存器处理。对于 `add` 这样的短函数，调用过程本身可能和函数主体一样“显眼”。

但如果编译器把 `add` 内联，调用处可能直接变成：

```asm
    MOVS    r0, #1
    MOVS    r1, #2
    ADDS    r0, r0, r1
```

可以发现，这段代码中已经没有 `BL add`，也没有进入 `add` 函数后再通过 `BX lr` 返回。原来需要经过“跳转到函数，再跳回来”的过程，现在直接在当前位置完成加法。

这就是内联可能带来的效率提升。对于 Cortex-M 这类微控制器来说，减少一次函数跳转和返回，可以减少执行的指令数量，也可以减少处理器流水线因跳转产生的影响。函数越短、调用越频繁，调用开销在总执行时间中所占的比例通常越明显。

读到这里，可能会有人有疑问：为什么在阅读大佬的项目源码时通常都使用 `static inline` 而不是 `inline` 呢？这两种使用方法又有什么区别呢？

## 三、inline与static inline

事实上，`static` 和 `inline` 解决的是两件不同的事。`static` 决定的是函数能不能被其他源文件看见，`inline` 则是给编译器的内联建议。

```c
static inline int add(int a, int b)
{
    return a + b;
}
```

`static` 关键字使得函数具有内部链接，符号只在当前 `.o` 文件内可见，别的 `.o` 看不到。如果没有 `static` 关键字，则在编译时编译器会认为它是全局的，就会像普通函数一样编译。所以，加入 `static` 后可以有效避免全局符号污染，不会和库或其他模块的同名函数冲突，帮助编译器优化。因此这里建议大家在使用 `inline` 关键字的时候最好加上 `static` 关键字一起使用。另外在 C99 规则下，单独写 `inline` 放在 `.c` 里，即使只在本文件使用，也可能链接失败，此处不做详细的展开说明。

需要注意的是，如果把 `static inline` 放在头文件中时，则每个包含它的源文件都可以得到一份自己的函数定义，链接器不会把它们当作同一个外部函数。但是如果是在源文件中进行定义，在头文件中仅作声明，则其他包含该头文件的源文件反而会出错，因为 `static` 决定了该函数不能被其他源文件看见，所以在链接时，链接器会发现源文件没有提供外部定义而因此报错。

```c
#ifndef MATH_UTIL_H
#define MATH_UTIL_H

static inline int add(int a, int b)
{
    return a + b;
}

#endif
```

## 四、内联函数和宏定义

宏在预处理阶段展开，本质上是文本替换：

```c
#define SQUARE(x) ((x) * (x))
```

宏没有真正的参数类型检查，也可能重复计算参数。忘记括号时，`SQUARE(a + 1)` 甚至会被展开成 `a + 1 * a + 1`。而内联函数是真正的函数，参数有明确类型，也不会因为展开而重复求值。

但是，宏仍然有自己的用途，例如条件编译和标识符拼接中仍然无法替代。但对于类型明确的数值计算、位操作和寄存器访问，使用 `static inline` 通常更容易检查和维护。

## 五、内联的好处和代价

内联可以有效地减少小函数的调用开销，也可能帮助编译器做常量传播。但是需要注意的是，`inline` 关键字是典型的用空间换时间的做法，函数代码被复制到多个调用位置后，程序体积也会增加，而众所周知嵌入式系统的 Flash 空间有限，过度内联可能导致程序变大，反而没有带来明显的速度收益。

因此，寄存器读写、位操作、简单的数据转换等比较适合使用 `static inline`，而复杂业务逻辑、递归函数以及局部变量很多的函数，不要为了追求“看起来更快”就加上 `inline`。最终是否变快，要看生成的汇编和实际运行结果。

## 六、总结

最后，把全文压缩成一句实用的话：`inline` 是优化建议，`static` 决定可见范围，而是否真正内联，要以编译器生成的代码为准。如果函数只在一个 `.c` 文件中使用，可以写成 `static inline`；如果函数需要被多个源文件调用，则需要在头文件中完成 `static inline` 函数的定义。
